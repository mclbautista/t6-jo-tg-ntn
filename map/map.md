## Destination

A build-ready spec for a Docker-hosted Telegram watchdog. It watches one intake topic, uses an LLM to decide whether each message is a Job Order and to extract its fields, writes it immediately to the existing Notion Job Orders database with status "Needs Intake Review", and reports problems to a private ops topic. The spec must be precise enough for an implementing agent to build it without coming back with questions.

The wider reason this matters: **Projects are built from Deliverables which are built from Job Orders.** A clean, always-populated Job Order layer is the base of a Job Order Health → Deliverable Health → Project Health rollup. This is why several design decisions (End of Shift's 23:59 fallback, Deliverable linking) favor a calculable, non-blank field over a strictly-literal one, with the trade-off made explicit and reported rather than silent.

## Notes

- Domain: post-production operations. Telegram forum-topic group in, Notion Job Orders database out (data source `collection://3d8fb4d5-9e59-8073-a0d0-000b77632947`). Volume is roughly 10-12 JO messages a day, so LLM cost and latency are not a constraint.
- Standing principles (name them in every resolution so they transfer):
  - **Precision over recall when a human can fill the gap**: a wrong link costs more than a blank, so the matcher links only what it affirms and hints the rest.
  - **Scope at the filter, not the grant**: broad access is fine when every lookup is re-scoped (chat and topic id for messages, project id for Deliverable candidates).
  - **Annotate, don't gate**: verification never blocks the Notion write. Problems are reported to the ops topic and the traffic coordinator cleans up.
  - **Never drop silently**: every candidate message ends in Notion, in the ops topic, or in an explicit ignore log.
  - **Idempotent writes**: the same Telegram message never creates two rows, even after a crash.
  - **Own your dedupe key**: one process, one ledger, one writer — the thing that decides "already captured" is never split across systems.
  - **Resolve, don't generate**: the LLM extracts raw mentions and raw text; deterministic code resolves identity, time, and canonical form.
  - **Decide by eval, not by reputation**: model/prompt choices are settled by running them against the sample corpus, not by spec-sheet comparison — explicitly and knowingly waived for LLM *provider selection* (owner's call) and for the Deliverable matcher's pre-launch gate (replaced by shadow mode), never for the matcher's per-JO link/hint decision.
  - **Blank is a fact, filler is a fabrication**: a poster's own placeholder ("-", "N/A") passes through verbatim; the model never invents one — with a documented, reported exception for derived (never stated) shift-based deadlines, which default to 23:59 rather than blank so Job Order Health stays calculable.
  - **Reproducible by default**: refined to *traceable* by default for the two LLM calls, which run unpinned "latest" models by owner's choice — every row instead stores the model id the API actually returned, so nothing is unaccountable even though nothing is pinned.
  - **Never grade on the training set**: few-shot examples and the eval set are disjoint.
  - **Schema is the contract**: writes and validation both go against Notion's live option names, never a hardcoded guess; the ledger schema itself is a documented, versioned contract other tools can read.
  - **Mask at the boundary, keep the source**: credentials are masked by deterministic code wherever text leaves the local ledger; the ledger and Telegram keep the original.
  - **A queue you can't inspect isn't a safety net**: the ledger is a plain, documented SQLite file, not a library's private store.
  - **Silence is a failure mode**: a missing daily heartbeat is itself the outage signal; accepted as the only detector for outages beyond Telegram's 24h retention window.
- Settled while charting:
  - Passive watching of one dedicated intake topic; chatter is filtered by an LLM call.
  - The LLM does the whole job: classification and field extraction (formats are inconsistent, plaintext, written by coordinators).
  - Verification = format checks + semantic checks, all deterministic (no LLM call in the verification step itself — the LLM's job ends at classify/extract). Verified or not, the JO goes to Notion. Status is "Needs Intake Review" (already exists in the database), with no separate pass/flag property.
  - Problem reports go to a separate private group/topic used only by the traffic coordinator, the lead technical supervisor and the owner. Ops-topic messages default to vertical, line-broken formatting (one fact per line) over comma-joined prose, and tag no one by default — only the specific person who has to act (Priya on human-decision checks; the owner on true outage alerts).
  - Strictly one-way capture, Telegram to Notion.
  - Message types in v1: text messages and forwards.
  - Single writer path to Notion, read-back after every write; one emoji reaction on the original message after a confirmed write, with a fixed meaning ("captured") that's never swapped to signal a problem.
  - Durable local queue with retries, idempotent writes keyed on chat + message id, operator alert after repeated failure.
  - Runs in a Docker container on an always-on machine.
  - Project codes and team members are read from Notion and cached; departments are also read from Notion and cached (confirmed — see the technical design ticket).
  - Classification and extraction is one structured LLM call (not two), returning verdict/confidence/reasons plus verbatim raw fields; the model never sees the people/project roster, today's date, or the reply chain.
  - Verification checks (deadline-in-past, deadline-expected-but-missing, blank Task/Title, header-date-vs-posting mismatch, plus the checks that already lived in earlier tickets) all post immediately and individually to the ops topic — binary report/don't-report, no severity tiers, no digest.
  - Credentials in raw text are masked by one deterministic masker (label followed by `:` or `=`, then the value) before the LLM call and before text goes to the Notion body, ops reports, heartbeat and logs; the unmasked original lives only in the ledger with owner-only permissions. Masked count appears on the daily heartbeat.
  - **Architecture is closed** (technical design ticket): one Python 3.12 asyncio process, pure `core/` with no I/O, `adapters/` for Telegram (aiogram `Bot` + our own offset loop)/Notion (hand-written `httpx`)/DeepSeek (classify-extract)/Jev (Deliverable matcher, redesigned around its typed Choice interface — no name echo). Queue is built on the ledger itself, not a separate library. n8n is builder-only tooling in v1, kept viable later via a `core/` CLI and a documented ledger schema; nothing outside this process ever writes a JO's Notion row.
  - Pipeline states: `received` → `extracted` → `planned` (exact Notion payload stored) → `writing` → `written` → `done`. The `writing` state plus a `Telegram Key` reconciliation query on restart closes the crash window around the Notion POST.
  - Ops posts are durable (outbox table, same transaction as `written`); the capture reaction stays best-effort.
  - Caches (People, Projects, Departments) persist as ledger snapshots; a stale cache is a normal miss, an empty cache blocks planning instead of resolving everything as a false miss.
  - Straight to live at go-live, no staged dry-run day; `dry_run: true` stays available in config as an off-by-default rollback tool. The Deliverable matcher's own `deliverable_link_enabled` flag is the one staged rollout that remains, because a wrong link is the one failure that stays silently plausible.
  - No model-version pinning, by owner's explicit choice — both LLM providers run "latest," with the returned model id stored per call and a heartbeat line only on change.
  - LLM usage/cost visibility resolved as a deliberate non-feature: token counts stored per call, queryable on demand, no dashboard or heartbeat line.
  - Outages beyond Telegram's 24h retention window are a documented, accepted gap — detection is the ops-topic's human members noticing a missing heartbeat, no external uptime service.
- Facts verified in the Job Orders database (fetched 2026-09-28):
  - Status options include "Needs Intake Review", "Pending", "In progress", "Needs Completion Review", "Done", "Cancelled".
  - Department options are TOC, AE, OE, COOR, COLOR, VFX, SOUND, ADMIN — read live, not hard-coded.
  - Assigned, Coordinator and cc are relations to a People data source; Projects is a relation to the Projects data source; Deliverable is a relation to a Deliverables data source. Relations need page ids, not names.
  - Text properties: JO Number, Title, Subtitle, Task, Purpose, Notes, Blocker, Source / Source Drive, Platform, Watermark, Link Settings, Mode of Transfer. Date properties: Date, Deadline. Title property: Name. Health is a read-only formula.
  - New text columns added by the owner on 2026-09-28: `Telegram Key` and `Pending` (verified). Poster is recorded in the page body, not a property.
- Facts verified in the Contacts database (fetched 2026-09-29, `collection://77b2a701-71db-4e88-a694-37f07303e77e`):
  - `Aliases` — Text, comma-separated.
  - `End of Shift` — Select, 24 hourly options (`12:00 AM` through `11:00 PM`) plus `Flexible / Variable`.
  - `TelegramHandle`, `TelegramUserID` already existed as Text.
  - Pages are named after the person (the `Name` title property), which is what the guarded fuzzy-match step matches against.
- Jev and DeepSeek are the two LLM providers, chosen directly by the owner (no bake-off): DeepSeek (OpenAI-compatible JSON mode) for classify/extract, Jev (a System One typed-decision model, not generative) for the Deliverable matcher only. Both run unpinned "latest," traced by storing the returned model id per call. Laya is dropped.
- Telegram's forward metadata only exposes enough to build a real link back to the original message for one of the four origin types (`channel` — has chat + message id); `user`, `hidden_user` and `chat` origins carry no message-level reference at all, which is a Telegram data-model limit, not a resolvability gap.
- Telegram's reaction set is fetched live per-chat via `getAvailableReactions` and can be further restricted by the group admin — there's no fixed global list to pick an emoji from ahead of time (plain ✅ likely isn't offered). The actual "captured" emoji is a build-time pick against the real group, not a design decision.
- The owner's real Telegram handle isn't on file; `@cyril`-style tags in the mock-ups are placeholders, resolved to the real handle in config at build time, same as chat/topic ids.
- Deliverable matching is a separate Jev call run after extraction and project resolution, before the single Notion write. It's a per-candidate typed Choice question (not a name-echo call — see the technical design ticket's redesign), keyed by page id, scored by probability against `T_link`/`T_hint` config thresholds. Ships in shadow mode (`deliverable_link_enabled` default off) rather than behind a pre-launch labeled eval.
- Facts verified in the Deliverables database (fetched 2026-09-28): 9 rows, each with a `🗺️ Projects` relation and a two-way `Job Orders` relation; Status lifecycle Staged → Archived; Class Master or Archival; `OCP Intake ID` and `OCP Intake Source` are empty. Only 3 real JO-to-Deliverable pairs exist today (fixed regression fixtures).

## Decisions so far

<!-- one line per closed ticket: [title](tickets/<file>): gist -->

- [Telegram Bot API capabilities and limits](tickets/telegram-bot-api-capabilities.md): the bot can see every intake message (privacy mode off or admin), filter by topic thread id, read four forward-origin types, set one reaction per message, drop edits at the API, post into another group's topic, and long polling suits the volume.
- [Notion write path for Job Orders](tickets/notion-write-path.md): a container writes with the REST API and an internal integration (Read and Insert content, three databases shared — now four, see Deliverable matching below), rows need exact schema names and page ids for relations, text items cap at 2000 characters, there is no documented idempotency header so dedupe is ours, and a few behaviors are left for a build-time smoke test.
- [Job Order field mapping into Notion](tickets/job-order-field-mapping.md): every property has a rule (canonical Name, verbatim text, Subtitle and Pending inferred/filled, datetimes in Asia/Manila with 23:59 for a bare day, status always Needs Intake Review, department exact match, Coordinator blank in v1, Deliverable no longer always blank — see Deliverable matching); raw text and a source block go in the body; new Telegram Key and Pending columns exist; Priya is a standing cc.
- [Sample corpus of real intake messages](tickets/sample-corpus-redacted.md): 77 genuine JOs from 31 projects (redacted copy in assets); headers and labels vary widely, a third of deadlines are vague phrases, exact re-posts and reused numbers occur, and the corpus has no chatter, near-misses or paired Notion rows.
- [Reliability, outages and operations](tickets/reliability-and-operations.md): bot is admin of the intake group only and every message is filtered on chat+topic id; SQLite queue on a host bind-mount; 5-attempt backoff (30s→10m between attempts) then one ops-topic alert with the message kept, never dropped; daily heartbeat; secrets via Compose env, restart: unless-stopped; Telegram confirms a 24-hour update-retention window, which is what makes short restarts safe.
- [Resolving people and projects from free text](tickets/resolve-people-and-projects.md): the LLM only extracts raw mentions, a deterministic step resolves them; people match on Telegram user id, then handle, then a nickname alias table (now Contacts `Aliases` plus a guarded fuzzy step — see the technical design ticket), then projects match against the 142-value Project Code select, longest-code-first; no/ambiguous match leaves the relation blank and reports to ops; Assigned can hold several ids; caches refresh on start and every 6 hours; poster identity stays out of Coordinator.
- [Deadline phrases](tickets/deadline-phrases.md): shift phrases resolve via each person's exact `End of Shift` hour (Contacts, not a coarse day/night flag), using the next occurrence at or after posting time and the latest across assignees when several apply, defaulting to 23:59 on the posting day (reported) when a shift is blank/`Flexible` or nobody resolves — see the technical design ticket's §9 for the full reasoning; "tonight" reuses the existing 23:59 default; ASAP still gets a shift-based Deadline but is flagged high-priority in the ops report; phrases with no clock meaning stay blank; hedges are stripped from Deadline but kept in Notes; a pre-posting deadline is kept as stated and reported, never rolled forward; the original phrase always also lands in Notes.
- [Forwarded Job Orders](tickets/forwarded-job-orders.md): source block records both the forwarder ("posted by") and the original author when resolvable ("originally from"); Date and deadline math always use the forward time, never the original time; each origin type (user/hidden_user/chat/channel) always records something in the source block; any non-`user` origin is reported to ops; the LLM sees origin metadata for classification only, never as a source of field values.
- [Re-posts, duplicates and idempotency](tickets/reposts-duplicates-idempotency.md): edits are received (not filtered) and reported to ops without touching the row; Telegram Key is `chat_id:message_id`; content-level duplicate detection runs against the local ledger, keyed on project+department+number as a parsed integer, and is skipped (not flagged, exact re-posts included) when any piece doesn't resolve; an exact re-post or a reused number always creates a new row, never skips or merges, and is always flagged to ops and in the new row's Notes.
- [Classifier and extractor: model and call design](tickets/classifier-and-extractor-design.md): DeepSeek is the provider (JSON mode + Pydantic validation, no Jev/Laya bake-off — see the technical design ticket); one structured call returns verdict/confidence/reasons plus verbatim raw fields, never a resolved datetime or id; the model sees only text/caption plus forward-origin metadata, never the roster, today's date, or the reply chain; three verdicts (`jo` writes normally, `unsure` writes and flags ops, `not_jo` goes to an ignore log with no per-message alert); no-text forwards skip the LLM and log as `no_text`; multiple JOs in one message still produce exactly one row, flagged `multiple_jo_suspected`; LLM outages queue and alert rather than writing a bare row; runs unpinned "latest" at temperature 0, with the returned model id stored per message; few-shot examples (~15) and the eval set (~60) are disjoint.
- [Verification rules and ops-topic reporting](tickets/verification-and-ops-reporting.md): four new deterministic checks (deadline in the past, deadline expected but unparsed, blank Task/Title, header-date-vs-posting mismatch) join five already decided elsewhere; severity is binary, not tiered; reports carry the Notion row link, JO name, triggered checks, model reasons where relevant, an intake-topic message link always, and an original-message link only for channel-origin forwards (the only origin type with enough metadata); no @mention by default except Priya on checks that need her hand; reports post immediately, no digest; schema validation runs against the existing 6-hour cache; the capture reaction has one fixed meaning and is never swapped to signal a problem, and a failed reaction call retries briefly then gets counted in the daily heartbeat rather than alerted per message.
- [Ops-topic message mock-ups](tickets/ops-topic-mockups.md): five locked message formats (flagged JO, unresolved person/project, duplicate/reused number, outage alert, daily heartbeat), all vertical/line-broken rather than comma-joined; no tag by default, Priya tagged on the human-decision checks, the owner tagged specifically on the 5-attempt-retry outage alert; the heartbeat shows ignored messages' actual first lines, not just a count. Superseded in parts by later amendments (Passwords withheld line; 4 Deliverable lines; probability-based hint; Model changed line; fuzzy-match line) — see `amendment-log.md`.
- [Secrets in raw text](tickets/secrets-in-raw-text.md): only passwords/credentials are masked (label `pw`/`pass`/`password`/`passcode`/`PIN` immediately followed by `:` or `=`, so link-setting phrases like "dl with pw" are untouched); links stay as posted; detection is deterministic code, never the LLM; masking runs before the LLM call and on every path out of the ledger (Notion body, ops reports, heartbeat first lines, logs), replacing the value with `[password withheld – see Telegram message]`; the unmasked original stays in the ledger with owner-only permissions; no per-message ops post, just a heartbeat count; unlabeled passwords are an accepted v1 false negative; the masker version is stored per message for replay.
- [Deliverable matching](tickets/deliverable-matching.md): link-only, never creates a Deliverable page; needs a resolved Project and queries that project's Deliverables live (not the 6-hour cache) with no status or class filter; redesigned in the technical design ticket around Jev's typed Choice interface (per-candidate probability, no name echo, no `reason` text); only a probability-thresholded `match` is linked, `maybe`/ambiguous cases hint to ops with a probability, a plain no-match is silent (counted in the heartbeat as four lines); zero to many links per JO; no backfill; a matcher failure retries once, writes the row with a blank Deliverable and posts one ops line; the ledger stores model id, prompt tag and the candidate snapshot; ships in shadow mode (`deliverable_link_enabled` default off) rather than gated on a pre-launch labeled eval. Amends field mapping (Deliverable no longer always blank), the Notion write path (Deliverables must also be shared with the integration) and the ops mock-ups (heartbeat lines and the hint format).
- [Technical design and architecture](technical-design-and-architecture.md): closes the build spec — process/repo topology, library choices (aiogram-as-client not Dispatcher, hand-written Notion adapter, DeepSeek + Jev split, ledger-native queue, hand-rolled deadline parser), the `received→…→done` pipeline state machine and the `writing`-state crash-window fix, Contacts-based person resolution with a guarded fuzzy step, the End-of-Shift 23:59 fallback and its reasoning, durability rules for ops posts vs. reactions vs. caches, config/secrets/logging shape, the four-layer test strategy, straight-to-live deployment, and the tracer-bullet build-ticket order. See `amendment-log.md` for every statement this supersedes.

## Out of scope

- Write-back or status sync from Notion to Telegram (one-way capture only).
- Applying edited or deleted Telegram messages to existing rows (a correction needs a fresh post). An edit to an already-captured message is received and reported to ops ("edited after capture, row not updated"), never applied to the row.
- Photos, files without captions, and multi-message JOs.
- Replies to posters in the thread (only the emoji reaction).
- Correcting old rows whose datetime deadlines were stored as UTC but meant as Manila time (confirmed 9 p.m. Manila; they read 8 hours late). Duration reports that mix old and new rows stay off until someone fixes them, outside this watchdog.
- Masking unlabeled credentials or link-embedded keys in v1 (see Secrets in raw text).
- Model-version pinning and a version-bump routine for DeepSeek/Jev (owner's explicit choice — traced instead, per the technical design ticket).
- A staged dry-run phase at go-live, and an external uptime check for outages beyond 24 hours (both owner's explicit choice, per the technical design ticket).
